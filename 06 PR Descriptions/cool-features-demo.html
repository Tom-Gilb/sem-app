[!] Expert Analysis — Core Planning Engine

The foundation is the 9-Step Evo Cycle — proven from 1970s NASA/IBM projects to today's software organisations. Decompose and Prioritise are distinct, separate events; combining them (as most tools do) is the single biggest cause of mis-prioritised work. The key innovation here: planning stages are cyclic workspaces, not sequential gates. You can — and should — loop back from Measure to Spec when delivery reveals that your current Values don't match what stakeholders actually experienced.

The Function Binary Rule (DD-004) is one of Planguage's most counter-intuitive principles: a Function is either present or absent — full stop. Quality attaches as a Value entry. This means planners cannot hide ambiguity inside a Function description ("user-friendly login") — quality must be stated separately, measurably.

The SUCCESS Definition (DD-006) measures across 5 axes: Values reached, Functions present, Constraints respected, Conditions satisfied, Resource Budgets respected. A plan is never "done enough" — it is either within all bounds or it isn't. There is no partial success badge.

🔺 Penta Model & SVERD

[!] Expert Analysis — Penta Model & SVERD

SVERD (Stakeholders · Values · Efficiency · Resources · Design) is the complete ontology of any plan. It was co-invented by Tom Gilb and Al Shalloway in 2022 as a visual representation of how the 5 fundamental planning dimensions interrelate. The pinwheel makes visible what most planning tools hide: the direct relationship between Resource investment and Value achievement.

The Efficiency score at the centre (Value achievement ÷ Resource utilisation) is the only metric that ultimately matters: are you getting Value relative to what you're spending? A plan with 100% on-time delivery but 40% Value achievement is not a success — SEM shows this immediately.

The 3-Ring Design hierarchy (Solutions → Evo Steps → Tasks) encodes a key Planguage insight: Solutions are the DESIGN decisions at the architecture level; Evo Steps decompose Solutions into delivery increments; Tasks decompose further into work units. Hierarchy radiates outward from the core — denser decisions at centre, implementation detail at the edge.

The Governance + Cascade Tracking system encodes a truth most planning tools ignore: changing a Value Goal propagates downstream. Solutions must be redesigned, Resource budgets re-estimated, Evo Steps re-sequenced. "Cascade Not Yet Calculated" is an honest declaration, not a failure state.

[!] Expert Analysis — Sharpening Interviews

The Sharpening Interviews are designed with one purpose: to surface the questions planners never ask themselves. The 26-theme Solution Sharpening interview spans Architecture Level Thinking, Reusability, Simplification, Adaptability, Reversibility, International scale, Competitiveness, Innovation, and 18 further dimensions. Each theme represents a class of design failure that Gilb has documented across decades of project post-mortems.

Architecture Level Thinking alone (Theme 1) typically surfaces 3–8× more value potential than any local optimisation. Most development teams optimise within the wrong system boundary — this theme forces them to question the boundary itself before optimising within it.

The [?!"] Justification system creates a permanent audit trail. Every answer is backed by evidence — not just what the planner decided, but WHY (Analysis [!]), from WHAT source (["] with citation), and with what confidence (Credibility 0–10). This is analogous to Gilb's IET Evidence + IET Source + ±Uncertainty in Competitive Engineering. A plan that cannot be justified is a plan that cannot be defended.

The 4 selection modes (Mixed / All / My answer only / Ticked only) give the planner precise control over which AI suggestions enter the effective answer — tick what resonates, type what's unique, combine freely.

Competitive Engineering ch.14: "Architecture-level solutions deliver 3–8× more value than local patches."

[!] Expert Analysis — AI & Agent Tools

The key architectural principle: AI is Claudian (external to the app), not embedded. This means AI quality equals model quality, not API budget. The SEM App contains zero embedded API calls — all AI happens in Claudian (this session), writing structured results to files the SEM App reads. No user API key needed. Resilient to provider changes.

The KISS Panel (Keep Improvement Super Surprising) is the most analytically powerful tool. It doesn't ask "what should we do?" — it mathematically computes which constraints, goals, or solutions, if changed, deliver the highest Value/Resource ratio. The 5 improvement types are ranked by ROI: Constraint relaxation (4.1×) consistently outperforms adding new Solutions (3.8×), because a constraint is a hard ceiling — removing it immediately unlocks all solutions blocked beneath it.

The Conjunction-of-Technologies principle governs every AI prompt: the full Planguage JSON is always passed (not a prose summary), and every AI suggestion carries a source-layer badge — Derived from plan / Cited from Gilb / LLM training / Internet-fetched. This makes AI reasoning transparent and auditable, not a black box.

Model selection matters: Haiku is banned for structural work. One Haiku debacle cost 11 hours of debugging work that Sonnet would have resolved in minutes. The economy of cheap models is false — it transfers cost from API tokens to human time, at the worst exchange rate possible.

[!] Expert Analysis — Visualization

The Value Flow Diagram makes explicit what most architecture diagrams hide: causal chains from Functions through Solutions to Values. When a planner can see "this Solution delivers 42% of this Value" as a visual arc with magnitude, they make better trade-off decisions. Most project visualisations show work — Evo diagrams show impact.

The V × Step VDT Table (Value Decision Table) is Planguage's answer to the question "which Evo Step matters most?" — it maps every Value against every Evo Step, showing expected impact per cell. Empty cells are not blanks to be ignored; they are prompts: "Have you assessed whether this Step affects this Value? If not, why not?"

The OPTIMA MultiVision sliders implement the Tolerable/Goal/Wish commitment spectrum visually. Moving a slider from 50 (Goal) to 100 (Wish) is not just aspirational — it immediately shows the consequence: which Solutions become insufficient, which constraints become binding, what new Resources are needed. The plan reacts to the vision, not the other way around.

Gilb's SEM Diagrams concept (DD-005): "ONE panel where all 4 knowledge sources merge against the spec — Functions as central spine, Values and Resources as satellites, Means with impact magnitudes."

[!] Expert Analysis — Export & Email

The flat-table email standard is not a cosmetic choice. It is a precision communication tool: each entry type rendered in its canonical Planguage colour (violet=Value, green=Function, orange=Solution, red=Constraint, blue=Stakeholder) so any recipient immediately identifies what type of planning assertion they are reading — without reading a legend.

The Keynote compatibility requirement drove five design constraints: no nested tables (Keynote splits them into free-floating separate tables), no div backgrounds (stripped by Keynote), explicit bgcolor= attributes on every cell, no height= on text cells (Keynote treats it as maximum, clips wrapped lines), and pre-split long text into one-line-per-row. Every constraint was discovered by Tom's screenshot and resolved by Claudian — a five-round iterative process.

The Auto-Open Mail + clipboard pattern encodes a precise UX contract: mailto: fires Mail.app automatically (auto-open beats zero-paste); the colourful HTML goes to the clipboard; one ⌘V paste in the Mail compose window upgrades the body from plain text to full colour. The LOUD "PASTE ⌘V HERE FOR COLOR VERSION" cue at the top of every email body is non-negotiable — Tom's muscle memory depends on it appearing in the same position every time.

[!] Expert Analysis — Governance & Version Control

The Plan Health Index (PHI) scores a plan across five dimensions: completeness, clarity, feasibility, constraint-satisfaction, and Value coverage. Each dimension has an Expert Why? paragraph with a mandatory URL citation — planners must be able to verify the reasoning, not just accept a score. A PHI without citations is an opinion; with citations it is a standard.

The No-Silent-Removal rule was ratified after a single commit (d6db016) silently dropped 8 permanent-surface affordances — none caught by Claudian, all discovered by Tom. The rule is simple: never remove any element of a permanent surface without explicit Tom approval, obtained beforehand. The list of known silent-drop incidents is maintained as an audit log and reviewed every session.

The Consequence Cascade system implements the principle that planning changes are never local. Changing a Value Goal propagates: Solutions may need redesign (direct), Resource costs change (2nd-order), Value delivery is affected (nth-order). "Cascade Not Yet Calculated" is not a failure — it is an honest declaration that downstream analysis has not yet been done. Most planning tools pretend this propagation does not exist.

The Weekly Full Backup was ratified after the 2026-05-19 disaster (git reset --hard destroyed 8 days of work). Two layers: surgical prompt files (fast, small) + full app tar.gz (~4MB, excludes node_modules). Both refreshed every session start. History is never auto-deleted — the backlog of timestamped backups is itself a safety net.

🧭 Navigation & UX Rules
14 Tools
[!] Expert Analysis — Navigation & UX Rules

The MOVE Principle (Make Options Visible Easily) was named by Tom Gilb in 2026. It encodes a fundamental UX truth: cognitive load from hidden options costs more than the screen space saved by hiding them. Every option the user might want at a given moment must be visible without scroll-hunt, menu-dive, or recall-from-memory. Friction-by-design is the enemy.

The Top-and-Bottom Navigation Mirror (DD-014) solves a specific usability failure: when a planner finishes a long sharpening interview, they are at the bottom of the page. Making them scroll back up to click "Next" is friction-by-design. Every navigation control at the top mirrors at the bottom when content scrolls past one viewport. This is not a nice-to-have — it is binding for every new surface.

The Interaction Disclosure rule (DD-009) implements "Zero-Training UI": no user should ever need to read a manual, be taught by someone else, or discover behaviour by accident. Every button has a title. Every multi-mode element (single-click AND double-click) lists ALL modes in its tooltip. Non-obvious interactions (drag, long-press, Cmd-click) are never silent.

The Loading State rule (Rule 8) has no exceptions: every spinner must have ALL FOUR elements — spinner, elapsed seconds counter, asymptotic % progress bar, and amuse content (8 rotating domain-relevant fact cards). A bare spinner leaves the user wondering if the app is frozen. The elapsed seconds counter is the most important element: it transforms "is this broken?" into "it has been working for 12 seconds."

🎨 Glyphs & Icon System

[!] Expert Analysis — Glyphs & Icon System

The Planguage glyph system is 25 years old. The keyed notation ([ ], *, →, !) is mathematically international — brackets and asterisks carry the same meaning in Japanese, Arabic, and English. F/V/S/C/R abbreviations were banned because they encode the English names of Planguage concepts, making the system unusable in other languages. Tom Gilb: "I want international icons."

The two-family glyph system (Color Keyed Icon + Color Artsy Icon) encodes a cognitive-economy principle: users learn one basic shape, recognise it in two variations. The Color Keyed Icon is the scientific form — literal keyed characters rendered with hand-stroke quality. The Color Artsy Icon is the artistic form — creative interpretation of the same concept. Same shape, two variations — users never have to learn two different visual languages.

The colour regime is not decorative. Each of the 8 Planguage canonical colours (violet/green/red/orange/blue/dark-green/amber/slate) identifies a specific entry type. A recipient who sees a violet table in an email knows immediately they are reading Value entries — without reading a header. The colourful-HTML export and the glyph system are two facets of the same Conjunction-of-Technologies principle: colour does the semantic lifting that text alone cannot.

DD-017 (Color-on-Background Contrast) was ratified because Tom Gilb has red-green colorblindness. Dark green and red on dark backgrounds are unreadable for R-G colorblind users — a fact that affects 8% of male users globally. Canonical-colored text must always appear on a white background.

Tom Gilb, 2026-06-04: "The reason for my rule was that users did not have to learn 2 different visual shapes. One basic shape, 2 variations."

[!] Expert Analysis — Agent & Board Tools

The 10-agent architecture maps exactly to the 9-step Evo cycle: each agent specialises in one stage of the planning cycle. Agent #1 (Evo Sharp Interview) operates at Stage 10 — sharpening by iteration. Agent #2 (Evo Planner) generates the delivery plan at Stage 6. Agent #3 (Step Improvement + FEED ME!) improves individual Evo Steps. Agents #4–#8 cover Domain Models, Stakeholders, Critical Analysis, Plan Composition, and Decision Support.

The Planguage Analyzer (Agent unified) is the full Conjunction-of-Technologies realisation: one panel that merges all 4 knowledge sources (current plan / Gilb corpus / LLM training / internet) against the spec, with per-finding source-layer badges. Every finding is attributed to its source — planners know whether they are reading a deterministic calculation, a Gilb citation, a general LLM suggestion, or a live internet finding.

The Standards Auditor reads the current spec and checks it against Kai-Zen standards (Template_Write_*.md + Rule_Write_*.md). Returns per-defect violations with specific standard citations. This is not "AI says your plan is incomplete" — it is "Rule_Write_planguage-spec.md §4.3 requires a Scale for every Value entry; V.Deployment is missing one."

The Maria Board Agent operationalises the Planguage governance loop: board decisions become structured entries, meeting minutes become tracked changes, governance records become version history. The board is a stakeholder — its decisions affect Values, Constraints, and Resources. Maria makes that visible.

Conjunction-of-Technologies SUPREME principle: "Every Claudian prompt MUST pass the Planguage structure, not a natural-language summary. The spec JSON or relevant entry objects — NOT 'the plan is about X'."
